# Remote MCP with OAuth

Most launch brokers host an MCP server that clients reach over HTTP and authorize with OAuth.

## Discovery: protected-resource metadata

Four servers in the batch publish OAuth protected-resource metadata at `/.well-known/oauth-protected-resource`, which tells a client where to sign in and which scopes exist:

| Server | Authorization server | Scopes advertised | Source |
|---|---|---|---|
| Robinhood `agent.robinhood.com/mcp/trading` | the same URL | `internal` | [^rh-13] |
| Coinbase `agents.coinbase.com/mcp` | `login.coinbase.com` | portfolios, accounts, orders, trades, transfers, products | [^cb-04] |
| Webull `api.webull.com` | `api.webull.com` | `account:read`, `order:read`, `order:write`, `market:read`, `instrument:read`, `instruction:all` | [^wb-09] |
| Public `mcp.public.com` | listed in metadata | `trading.read`, `trading.write`, `marketdata`, `openid` | [^pu-05] |

Fine-grained scopes (Coinbase, Webull) let a client ask for less than full access. A single broad scope (Robinhood's `internal`) means account-level settings do the limiting instead.

## Client registration

- Robinhood: an independent test found a dynamic client registration endpoint and PKCE.[^rh-02]
- Coinbase: supports Dynamic Client Registration and Client ID Metadata Documents, but still allowlists clients; registration does not grant every scope or tool.[^cb-01]
- Alpaca: hosted MCP setups ship fixed OAuth client IDs per client app.[^al-03]

## Builder notes

- Read the metadata before you build a consent screen; it tells you what a token can do.
- Expect allowlisting. A working registration call does not mean your client may trade.[^cb-01]
